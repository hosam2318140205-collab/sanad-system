# النشر على Production — Supabase + Vercel

كل ما يخص الكود جاهز ومختبر. هذا الملف فيه فقط ما يُنفَّذ من لوحتي Supabase وVercel، بالترتيب.

> **لماذا الترتيب مهم:** أول مستخدم يُنشأ في المشروع يصبح **المالك** تلقائياً. لذلك نغلق التسجيل العام أولاً، ثم ننشئ حسابك.

---

## أولاً: Supabase

### 1. إنشاء المشروع
- **New project** → اختر اسماً وكلمة مرور قوية لقاعدة البيانات واحفظها.
- **Region:** اختر **Frankfurt (eu-central-1)** — التطبيق مضبوط على خوادم Vercel في فرانكفورت (`fra1`) لتكون الاستجابة أسرع. إذا اخترت منطقة أخرى أخبرني لأغيّر `vercel.json`.

### 2. إغلاق التسجيل العام (قبل أي شيء آخر)
**Authentication → Sign In / Providers** → أطفئ **Allow new users to sign up** → Save.

### 3. إنشاء قاعدة البيانات
**SQL Editor → New query** → الصق محتوى الملف:

```
pos-app/supabase/setup/01_all_migrations.sql
```

→ **Run**. النتيجة المتوقعة: `Success. No rows returned`.
الملف يعمل كمعاملة واحدة: إما ينجح كله أو لا يتغير شيء.

### 4. إنشاء حساب المالك
**Authentication → Users → Add user → Create new user**
- البريد وكلمة مرور قوية (12 حرفاً على الأقل)
- فعّل **Auto Confirm User**

للتأكد، في SQL Editor:
```sql
select email, role, is_active from public.profiles;
```
يجب أن يظهر حسابك بـ `owner` و `true`.

### 5. بيانات تجريبية (اختياري)
في SQL Editor نفّذ `pos-app/supabase/setup/02_demo_data.sql`
(3 منتجات، 10 مقاسات/ألوان بباركود يبدأ بـ 299، عميل واحد — كلها معلَّمة للحذف).

### 6. نسخ المفاتيح
**Project Settings → API Keys** (أو **API**):

| القيمة | أين تجدها | سرّية؟ |
|---|---|---|
| Project URL | `https://xxxx.supabase.co` | لا |
| anon / publishable key | `anon public` أو `sb_publishable_…` | لا |
| service_role / secret key | `service_role` أو `sb_secret_…` | **نعم — لا تشاركه ولا تضعه في أي مكان غير Vercel** |

## ثانياً: Vercel

### 1. استيراد المشروع
**Add New → Project** → اختر مستودع **sanad-system** من GitHub.

### 2. الإعدادات
- **Root Directory:** اضغط Edit واختر **`pos-app`** ← مهم.
- Framework: Next.js (يُكتشف تلقائياً). اترك Build/Install كما هي — `vercel.json` يضبطها.

### 3. متغيرات البيئة (Environment Variables)

| Name | Value | ملاحظة |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Project URL | |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | anon / publishable key | **ليس** مفتاح service_role |
| `SUPABASE_SERVICE_ROLE_KEY` | service_role / secret key | فعّل **Sensitive**، وبدون `NEXT_PUBLIC_` |

- اختر البيئات: **Production** (و Preview إن أردت نسخ تجربة).
- إذا وُضع المفتاح السري بالخطأ في متغير `NEXT_PUBLIC_` **يفشل البناء تلقائياً** ولا يُنشر شيء.

### 4. Deploy
- البناء يشغّل تلقائياً: TypeScript + Lint + التحقق من ملف الـ migrations + Production Build + فحص عدم وجود أسرار في ملفات المتصفح. أي فشل = لا نشر.
- Vercel ينشر فرع **main** كـ Production. الكود الحالي على فرع `claude/pos-clothing-store-app-zu7ac1` — ادمجه في main أولاً (أستطيع فتح Pull Request لك).

### 5. ربط الرابط بـ Supabase
بعد أول نشر انسخ رابط التطبيق (مثل `https://your-app.vercel.app`) ثم في Supabase:
**Authentication → URL Configuration → Site URL** = الرابط → Save.
(إن ربطت دوميناً خاصاً لاحقاً، حدّث هذه القيمة.)

## ثالثاً: التحقق بعد النشر (من الجوال، 5 دقائق)

1. **الدخول:** افتح الرابط وسجّل الدخول بحساب المالك.
2. **الإعدادات:** اسم المتجر، **الرقم الضريبي** (15 رقماً)، السجل التجاري، العنوان → حفظ.
3. **الصور:** المنتجات → افتح منتجاً → ارفع صورة أو التقطها → حفظ → تأكد أنها تظهر في شاشة البيع.
4. **الباركود:** في شاشة البيع امسح أو اكتب `2990000000019` (إن أضفت البيانات التجريبية) → يُضاف للسلة.
5. **البيع والطباعة:** أكمل البيع → **طباعة** → الفاتورة الحرارية مع رمز QR. ومن صفحة المنتج → **ملصقات الباركود** → طباعة.
6. **الموظفون:** المستخدمون → مستخدم جديد (كاشير) → سجّل الدخول به وتأكد أنه لا يرى التقارير والمنتجات.

**المسح بالكاميرا:** أول مرة يطلب المتصفح إذن الكاميرا — اختر «سماح». إن رُفض بالخطأ: في iPhone من الإعدادات ← Safari ← الكاميرا، وفي Android من قفل العنوان ← الأذونات. الكاميرا تعمل فقط عبر https (رابط Vercel آمن).

إعداد الطابعة الحرارية: من نافذة الطباعة اختر الطابعة، الهوامش **None/لا شيء**، وحجم الورق 80mm (أو 58mm حسب الطابعة، ويوجد اختيار العرض داخل نافذة الفاتورة).

---

## رابعاً: قبل الافتتاح الفعلي

1. **حذف البيانات التجريبية:** SQL Editor → `03_remove_demo_data.sql`.
2. **تصفير فواتير التجربة (اختياري ولا يمكن التراجع):** يحذف كل الفواتير والمرتجعات والمشتريات والجرد ويعيد ترقيم الفواتير من 1، ويُبقي المنتجات والعملاء والمستخدمين والإعدادات.
   افتح `04_reset_test_transactions.sql`، أزل `--` من سطر `set_config` في أعلاه، ثم Run. بعده شغّل `03_remove_demo_data.sql` مرة أخرى لحذف ما تبقى من الأصناف التجريبية.
3. **صور التجربة:** Storage → `product-images` (صور المنتجات) و `expense-receipts` (إيصالات المصروفات) → احذف ملفات التجربة يدوياً (Supabase لا يسمح بحذف الملفات عبر SQL).
4. اعمل **جرداً** لإدخال كمياتك الفعلية.

## تحديث مشروع قائم (عند إضافة ميزة جديدة لقاعدة البيانات)

المشروع الذي نُفّذ عليه `01_all_migrations.sql` سابقاً **لا يُعاد تنفيذ الملف الكامل عليه**. بدلاً من ذلك:

1. **ادمج الكود أولاً وانتظر** حتى ينتهي نشر Vercel (الحالة Ready).
2. **فوراً بعدها** في Supabase → **SQL Editor** نفّذ ملفات `pos-app/supabase/setup/upgrades/` **الجديدة فقط**، بالترتيب.
3. كل ملف يعمل كمعاملة واحدة: إن فشل لا يتغير شيء. وإن نُفّذ مرتين بالخطأ يرفض من أول سطر دون أي أثر.

> **لماذا هذا الترتيب:** ترقية الورديات تجعل البيع يتطلب وردية مفتوحة. لو نُفّذت قبل نشر الكود الجديد، يبقى التطبيق القديم (الذي لا يحتوي زر فتح الوردية) عاجزاً عن البيع حتى يكتمل النشر. أما الكود الجديد فيبيع بشكل طبيعي قبل الترقية، والفرق الوحيد أن صفحة الورديات وحفظ الإعدادات لا يعملان حتى تُنفَّذ الترقية — لذلك نفّذها مباشرة بعد النشر.

| الملف | الميزة |
|---|---|
| `upgrades/0006_shifts.sql` | الورديات وإغلاق الصندوق |
| `upgrades/0007_expenses.sql` | المصروفات وصافي الربح (يتطلب تنفيذ 0006 قبله) |
| `upgrades/0008_purchase_advisor.sql` | مساعد الشراء الذكي (دوال قراءة + إنشاء مسودة شراء فقط — لا يغيّر أي جدول) |

> بعد تنفيذ ترقية الورديات يصبح البيع متطلباً لوردية مفتوحة (الكاشير يفتحها من شاشة البيع). يمكن إيقاف ذلك من **الإعدادات**.

### Smart Inventory 2.0 (‏0013–0016) — قاعدة البيانات أولاً ثم الكود

| الملف | الميزة |
|---|---|
| `upgrades/0013_locations_transfers.sql` | المواقع ورصيد كل موقع والتحويلات. كل الرصيد الحالي يُسجَّل في الموقع الرئيسي بتاريخ إضافة الصنف |
| `upgrades/0014_smart_counts.sql` | الجرد لكل موقع |
| `upgrades/0015_inventory_intelligence.sql` | التوفر والمقاسات الناقصة والشاذ والراكد (قراءة فقط) |
| `upgrades/0016_decision_center.sql` | مركز القرارات |

- **الترتيب:** نفّذ 0013 ← 0014 ← 0015 ← 0016، ثم ادمج الكود مباشرة.
- **مستقلة عن 0009–0012** (المبيعات والعملاء): تعمل قبلها أو بعدها، والاختباران ناجحان بالترتيبين.
- **لماذا القاعدة أولاً:** الكود الجديد يستدعي دوال المواقع والجرد الجديدة. أما الكود القديم على القاعدة المرقّاة فيبيع ويستلم ويسوّي بشكل طبيعي (متجر بموقع واحد لا يتغير شيء). **الاستثناء الوحيد:** شاشة الجرد القديمة لا تفتح بين الترقية ونشر الكود، لأن الجرد أصبح «أعمى» للكاشير. لذلك لا تبدأ جرداً في تلك الدقائق.
- **بعد النشر:** أضف الفروع/المستودعات من «الفروع والمستودعات» وعيّن موقع كل موظف. ما دام هناك موقع واحد فقط، يبقى كل شيء كما كان.
- **تحقق سريع بعد الترقية (قراءة فقط):**
  ```sql
  select count(*) from product_variants v
   where v.stock_qty <> coalesce((select sum(qty) from location_stock s where s.variant_id = v.id), 0);  -- يجب أن يكون 0
  ```

## ملاحظات أمان

- المفتاح السري يُستخدم فقط في الخادم لإنشاء حسابات الموظفين؛ كل البيانات الأخرى تمر بصلاحيات RLS حسب دور المستخدم.
- الزائر غير المسجل لا يستطيع قراءة أي جدول، والكاشير لا يرى التكاليف والأرباح.
- رفع الصور: JPG/PNG/WebP فقط، حتى 5MB، وللمدير والمالك فقط.
- فعّل في Supabase: **Authentication → Attack Protection → Leaked password protection** (إن كانت متاحة في خطتك).
